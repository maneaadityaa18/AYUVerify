# AyurVerify — Dataset Specification

> **Purpose:** Define the dataset structure, supported classes, data sources, annotation workflow, preprocessing, train/validation/test split, and YOLOv8n training requirements for the AyurVerify SIH prototype.

---

# 1. Dataset Objective

AyurVerify requires an image dataset for identifying selected medicinal plants and Ayurvedic raw materials using **YOLOv8n object detection**.

The prototype will **not attempt to identify all medicinal plants in India**.

Instead, the SIH prototype will focus on a carefully selected set of approximately **10–15 medicinal plants/raw materials** that demonstrate:

* Visual identification
* Similar-looking material differentiation
* Raw-material identification
* Confidence-based prediction
* Risk assessment
* Expert escalation
* Supply-chain verification

The objective is to demonstrate the complete system workflow rather than maximize the number of supported species.

---

# 3. Why 15 Classes?

The prototype should prioritize:

```
15 well-curated classes
        >
100+ poorly trained classes
```

A smaller dataset allows the team to:

* Collect better images
* Clean duplicates
* Train faster
* Evaluate each class
* Investigate confusion between similar materials
* Demonstrate the system reliably

The architecture should remain expandable so additional materials can be added later.

---

# 4. Dataset Size Target

The target is approximately:

### Per class

```
150–250 images
```

### Recommended target

```
~200 images/class
```

For 15 classes:

```
15 × 200
≈ 3,000 images
```

The final number does not need to be exactly 3,000.

Quality is more important than hitting an exact number.

---

# 5. Image Diversity

Images should not all look identical.

The dataset should contain variations in:

### Background

* White/clean background
* Wooden surfaces
* Soil
* Agricultural environments
* Market environments
* Cloth/table surfaces

### Lighting

* Bright daylight
* Indoor lighting
* Slightly dark conditions
* Shadows

### Orientation

* Different angles
* Different rotations
* Different object orientations

### Distance

* Close-up
* Medium distance
* Different object sizes

### Physical condition

Where applicable:

* Fresh material
* Dried material
* Different sizes
* Different stages of drying

This is important because the real application will receive uncontrolled photographs.

# 8. Important: We Do NOT Manually Create YOLO TXT Files

The team should **not manually write annotation files**.

YOLO requires annotations such as:

```text
class_id x_center y_center width height
```

but these files should be generated by annotation software.

Recommended tool:

**Roboflow**

Workflow:

```text
Images
   ↓
Upload to Roboflow
   ↓
Create classes
   ↓
Annotate images
   ↓
Review annotations
   ↓
Generate dataset
   ↓
Export YOLOv8 format
   ↓
Download dataset
```

Roboflow will generate the required `.txt` annotation files automatically.

---

# 9. Why YOLO Needs TXT Files

YOLOv8 object detection needs to know:

```text
WHAT object is present?
WHERE is the object?
```

For example:

```text
Neem Leaf
```

must be associated with a bounding box.

A generated YOLO annotation might look like:

```text
0 0.512 0.487 0.734 0.821
```

This represents:

```text
class_id
x_center
y_center
width
height
```

All coordinates are normalized between `0` and `1`.

The team does **not** need to manually calculate these values.

# 10. Annotation Strategy

For each image:

### Single object

Draw one bounding box around the visible material.

Example:

```text
+-----------------------------+
|                             |
|        ┌────────────┐       |
|        │  NEEM      │       |
|        │   LEAF     │       |
|        └────────────┘       |
|                             |
+-----------------------------+
```

### Multiple objects

Annotate every supported object separately.

Example:

```text
Image
 ↓
Neem Leaf
Tulsi Leaf
Moringa Leaf

```

Each object receives its own bounding box and class.

---

# 11. Annotation Rules

### Rule 1

Bounding boxes should tightly surround the visible object.

### Rule 2

Avoid including excessive background.

### Rule 3

Do not annotate objects that are not part of the supported classes.

### Rule 4

If an object is severely obscured, consider excluding the image.

### Rule 5

If the class cannot be confidently determined visually, exclude the image from the training dataset.

### Rule 6

Do not create fake labels.

### Rule 7

Review annotations before training.

# 15. Train / Validation / Test Split

Recommended split:

```text
70% → Training
20% → Validation
10% → Testing
```

For approximately 200 images/class:

```text
140 → train
40  → validation
20  → test
```

The exact split may vary depending on the final dataset.

---

# 16. Prevent Data Leakage

Avoid putting near-identical images into different splits.

For example:

```text
Original image
Edited version
Cropped version
Brightness-adjusted version
```

should not be distributed across train and test.

Otherwise the model may appear more accurate than it actually is.

---

# 17. Duplicate Removal

Before training:

* Remove exact duplicates.
* Remove obvious near-duplicates.
* Remove corrupted files.
* Remove extremely low-quality images.
* Remove irrelevant images.
* Remove images belonging to the wrong class.

A clean dataset is more valuable than a larger dataset.

---

# 18. Image Quality Requirements

Preferred:

```text
JPEG
PNG
WebP
```

Recommended minimum:

```text
640 × 640
```

Higher-resolution source images are acceptable.

Images may be resized during the YOLO training pipeline.

Avoid:

* Extremely blurry images
* Completely dark images
* Completely overexposed images
* Tiny unrecognizable objects
* Images where the material is almost completely hidden

---

# 19. Data Augmentation

YOLO training may use augmentation to improve robustness.

Useful augmentations include:

* Horizontal flip
* Small rotation
* Scaling
* Translation
* Brightness variation
* Contrast variation
* Cropping

Avoid extreme augmentation that creates unrealistic plant/raw-material appearances.

---

# 20. Important Training Principle

The model should learn the **material**, not the background.

Bad dataset:

```text
All Neem images
        ↓
Same white background
```

The model may learn:

```text
white background = neem
```

Better dataset:

```text
Neem
 ↓
soil
table
market
hand-held
outdoor
indoor
different lighting
different angles
```

This makes the model more robust.

---

# 21. Similar-Class Testing

Special attention should be given to visually similar materials.

Examples:

```text
Ashwagandha Root
       vs
Shatavari Root
       vs
Mulethi
```

and:

```text
Neem Leaf
       vs
Moringa Leaf
```

The test dataset should contain challenging examples.

This allows the project to demonstrate the real problem of **misidentification**.

---

# 22. Unknown Material Handling

The model is trained only on supported classes.

Therefore:

```text
Unknown material
        ↓
No reliable known-class detection
        ↓
Low confidence / uncertain result
        ↓
Risk Engine
        ↓
Expert Review
```

Do not label every unknown image as one of the 15 supported classes.

---

# 23. Confidence Handling

YOLO confidence should be treated as an **AI prediction confidence**, not proof of authenticity.

Example:

```text
Ashwagandha Root
Confidence: 91%
```

means:

> The model predicts that the visual appearance is consistent with Ashwagandha Root.

It does not mean:

> The material is scientifically proven to be authentic.

The Risk Engine should use confidence together with image quality and other available signals.

# 26. Training Machine

The training machine should contain:

```text
Python
PyTorch
Ultralytics
CUDA-compatible NVIDIA drivers
YOLO dataset
```

Then training can be performed using:

```bash
yolo detect train model=yolov8n.pt data=data.yaml epochs=50 imgsz=640 batch=16
```

The exact:

```text
epochs
batch
imgsz
```

should be adjusted according to GPU memory and actual training behavior.

Do not assume these values are optimal before testing.

# 38. Relationship With AyurVerify

The dataset is only the **AI identification layer**.

It does not directly implement:

* Authentication
* Batch management
* Expert verification
* Supply-chain transfer
* QR tracking
* Verification history

Those are handled by the application backend.

The complete system is:

```text
                IMAGE
                  ↓
             YOLOv8n
                  ↓
       AI IDENTIFICATION
                  ↓
        CONFIDENCE SCORE
                  ↓
           RISK ENGINE
                  ↓
        ┌─────────┴─────────┐
        ↓                   ↓
    LOW/MEDIUM             HIGH
        ↓                   ↓
     BATCH             EXPERT REVIEW
        ↓                   ↓
        └─────────┬─────────┘
                  ↓
          VERIFICATION
                  ↓
         SUPPLY CHAIN
                  ↓
       TRACEABILITY HISTORY
```

# 40. Final Principle

> **The goal is not to train YOLOv8n on everything found in India's medicinal flora. The goal is to build a clean, realistic, evaluated prototype that demonstrates how AI-assisted identification can reduce misidentification risk and connect that result to expert verification and supply-chain traceability.**

A smaller, high-quality dataset with real-world variation is preferable to a huge, noisy dataset.

# 42. Important Scope Boundary

The dataset should **not** be presented as:

> "Complete Ayurvedic medicinal plant database."

It should be presented as:

> **"AyurVerify Prototype Dataset — selected medicinal plants and Ayurvedic raw materials for AI-assisted visual identification."**
